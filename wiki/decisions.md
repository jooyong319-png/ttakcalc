# 결정 기록 (왜 이렇게 만들었는지)

> 시간순으로 추가. 코드만 봐선 안 보이는 판단·기각한 대안·재발 방지 규칙을 남긴다.

## 프로젝트 시작 — 왜 계산기인가 (2026-07-30)
WhenStage(콘서트 캘린더) 다음 프로젝트를 찾으며 후보를 좁힌 과정:

1. **제약**: 게임 버티컬만 배제(운영자 회사가 게임 정보 커뮤니티라 직접 경쟁이 됨). 쿠폰·딜·
   어필리에이트 같은 메커니즘 자체는 다른 버티컬에서 문제없음.
2. **재사용 자산 판단**: 기술 스택보다 값진 건 ① LLM 리서처 자동화 파이프라인 ② "일정+알림"
   엔진 ③ SEO 실전 경험. → 처음엔 "엔진 재사용, 버티컬만 교체"(공모주/자격증 일정)를 추천했으나
   운영자가 **새로운 형태**를 원해 계산기·도구 모음으로 방향을 잡았다.
3. 클러스터는 급여·노동 / 부동산 / 금융 **셋 다** 담되(운영자 결정), 한 사이트 안에서 **순차 출시**
   하기로 절충 — 계산기는 틀리면 신뢰가 즉사하므로 12개를 대충 내는 것보다 4개를 정확히 내는 게 낫다.

## 시장 조사 결과 — 계산기는 레드오션 (2026-07-30)
착수 전 실제로 검색해 확인한 사실(추정 아님):
- **연봉 실수령액**: 대형(사람인·인크루트·잡코리아) + 신생 소규모 10곳 이상이 경쟁.
- **프리랜서 3.3%**: "틈새"로 예상했으나 첫 페이지에만 9곳 이상(salarycalc.kr, withholding.kr,
  k-calc.com, mydogu.com, savingtax.kr, pluuug.com …). 계산기 전용 도메인이 이미 다 선점됨.
- **육아휴직급여**: 정부 공식(고용24)까지 있어 신뢰도 경쟁 불가.
- 상위 노출되던 `toolcalc.co.kr`은 **호스팅 만료로 사망** → 만들었다 방치되는 사이트가 많다
  (= 수익이 잘 안 나거나 유지에 손이 간다는 신호).
- 잘하는 신생 사이트(`demoday.co.kr`)는 **이미 공제 내역 투명 공개 + 계산기 50개 + 가이드**를
  갖춤 → 처음에 세웠던 차별화 가설("근거를 보여주면 이긴다")은 이미 업계 표준이었다.

**핵심 문제**: 계산기는 계산 로직이 1년에 한 번 바뀌어서, 이 팀의 최대 무기인 "LLM 리서처가
매일 새 정보를 쌓는 파이프라인"이 작동하지 않는다. WhenStage가 강했던 이유(매일 새 공연이
쌓임)가 여기선 통하지 않는다.

## 그래서 "계산기 + 제도 변화 추적" 하이브리드 (2026-07-30)
계산기를 버리는 대신 **축을 하나 더 붙여** 무기가 작동하게 만들었다.
- **계산기** = 검색 유입 + 실용 도구(롱테일).
- **제도 변화 추적**(`/changes`) = 차별화·재방문·매일 쌓이는 콘텐츠. 최저임금 확정, 4대보험
  요율 개정, 육아휴직 제도 개편, 세법 개정 등을 리서처가 추적한다.
- 제도가 바뀌면 **계산기도 같은 날 갱신** → 방치된 경쟁 사이트를 이기는 지점이 바로 여기다.
- 나중에 알림(WhenStage의 웹푸시 자산)을 붙이면 "내 상황에 영향 주는 제도 변경 알림"이 된다.

## 요율을 데이터로 분리 — 연도별 버전 관리 (2026-07-30)
`data/rates.json`에 연도별로 요율·세율·한도를 담고, 계산 로직(`lib/calc/*`)은 **그 데이터만 보고**
계산한다. 코드에 숫자를 하드코딩하지 않는다.
- **이유 1**: 제도가 바뀌면 데이터만 추가하면 되고 코드는 안 건드린다(개정 대응 비용이 거의 0).
- **이유 2**: 과거 연도 데이터가 그대로 남아 **"2025년 기준으로 계산"이 가능**하다. 경쟁 사이트는
  대부분 올해치만 지원한다.
- **이유 3**: 같은 데이터가 `/changes` 페이지를 자동 생성한다 — 콘텐츠가 공짜로 따라온다.
- 각 항목에 `source`(근거 고시)와 `verifiedAt`(확인일)을 **필수**로 둬서, 나중에 자동화가
  "이 요율이 아직 유효한가"를 검증할 수 있게 했다.

## 소득세는 연말정산 방식 근사 — 간이세액표를 쓰지 않음 (2026-07-30)
실제 매월 원천징수는 국세청 **근로소득 간이세액표**(소득·부양가족 조합별 고정값 목록)를 따른다.
그 표를 전부 데이터로 넣는 대신, 연말정산과 같은 방식(근로소득공제 → 과세표준 → 산출세액 →
근로소득세액공제)으로 연간 세액을 구해 12로 나눈 **근사치**를 쓰기로 했다.
- 근거: 간이세액표와 몇 천 원 차이가 나지만 **어차피 연말정산으로 정산되는 금액**이고,
  표 전체를 유지·검증하는 비용이 정확도 이득보다 크다.
- 대신 **화면(FAQ·푸터)에 근사임을 명시**한다. "왜 급여명세서와 다른가"를 먼저 설명해
  신뢰를 잃지 않는 쪽을 택했다. 숨기고 정확한 척하는 것이 최악이다.

## ⚠️ 초기 요율 데이터는 미검증 상태로 시작 (2026-07-30)
`data/rates.json`의 2026년 값은 **검색 결과를 근거로 넣은 잠정치**다. 실서비스(도메인 연결·색인
요청) 전에 **국민연금공단·건강보험공단·국세청·고용노동부 공식 고시로 전 항목 재확인**하고
`verifiedAt`을 갱신해야 한다. 이 확인 전에는 외부에 공개하지 않는다.

## UI 컨셉 — "영수증·명세서" (2026-07-31)
초기 UI는 "서류·영수증 톤"이라고 이름만 붙였을 뿐 실제로는 **평범한 금융 사이트 룩**(밝은 회색
배경 + 파랑 액센트 + 둥근 카드)이었다. 운영자가 "기존 것과 확실히 다른 UI/UX"를 원해 방향을
다시 잡았고, 후보 셋(① 영수증·명세서 ② 터미널·계산기 기계 ③ 스위스 그리드) 중 ①을 택했다.

**선택 이유**: 계산기의 본질은 "이 돈이 어디로 갔는지 항목별로 보여주는 것"이고, 그걸 가장 오래
잘 해온 물건이 급여명세서·영수증이다. 우리 제품 원칙("근거를 다 보여준다")과 개념적으로 일치해
장식이 아니라 **정보 구조를 그대로 차용**할 수 있다. 터미널(②)은 룩은 독보적이지만 금융 신뢰감이
약하고, 스위스 그리드(③)는 정교하지 않으면 밋밋해질 위험이 커서 기각.

**구현한 시각 언어**
- 종이(오프화이트 + 옅은 격자 노이즈) + 따뜻한 먹색 잉크 + **도장 빨강**(확인·강조에만 절제 사용)
- **각진 모서리**(radius 3px) — 종이는 둥글지 않다
- **점선 리더**: `항목 ······· 금액`. `table-layout: fixed` + `th > span::after`의 flex 채움으로 구현.
  열 폭을 못 박아야 리더가 항상 같은 지점에서 끝난다
- **소계는 실선, 최종 금액은 이중선**(3px double) — 명세서 합계란의 관습
- 입력칸은 밑줄만 있는 **서식 기입란**, 숫자는 전부 우측정렬 등폭
- 헤더 상단 톱니(뜯긴 종이), 절취선 + 양끝 반원 노치, **회전한 확인 도장**(검증일 표시)
- 다크는 "**먹지(카본지)**" — 영수증 물성을 유지한 어두운 종이(라이트 전용으로 도망가지 않음)

**부수 효과**: SalaryCalculator가 쓰던 자체 CSS를 버리고 공통 `Breakdown`/`InputCard`/`Field`로
통합해 계산기 8종이 완전히 같은 시각 언어를 쓰게 됐다. 새 계산기를 추가할 때 조합만 하면 된다.

**접근성**: 재설계 후 axe로 라이트·다크 각 5페이지를 검사해 0건. 이 과정에서 `--ink-faint`가
작은 글씨에서 2.73:1로 미달인 걸 발견해 조정했다 — **종이 톤처럼 저채도 팔레트는 대비가 조용히
모자라기 쉬우므로 눈대중 금지**(통합 위키 accessibility.md의 계산기로 검증할 것).

## 2026-07-31 — UI 3차: "영수증" 폐기, **컬러 블록**으로 재설계

영수증 컨셉은 운영자 평가가 **"디자인이 너무 스팸같다"**였다. 누런 종이 + 붉은 도장 + 점선 +
톱니 헤더의 조합이 의도한 "명세서"가 아니라 **광고 전단지/스팸 메일**로 읽혔다. 한국 웹에서
누런 배경 + 빨강 강조는 실제로 그 용도로 너무 많이 쓰여서, 개념적 정합성만으로는 이 연상을
못 이긴다. → **컨셉이 옳아도 관습적 연상이 이기면 진 것이다.**

시안 5종(딥 네이비 / 그라데이션 글래스 / 다크 일렉트릭 / 컬러 블록 / 에디토리얼)을 실제
페이지로 만들어 `/preview/[n]`에서 비교했고, 운영자가 **4 컬러 블록**을 택했다.

**최종 시각 언어**
- 흰 배경 + 무채색 텍스트, 색은 **정보로만** 쓴다
- 갈래별 컬러 카드: 급여·노동 = 파랑, 부동산 = 초록, 금융 = 주황.
  계산기가 8개라 "무엇이 무슨 갈래인지"가 색으로 먼저 읽혀야 한다
- 3열 카드 그리드(900px 2열 / 560px 1열)
- 둥근 모서리(radius 14px), 그림자는 hover에만
- **결과 명세서(점선 리더·등폭 숫자·이중선 합계)는 그대로 남겼다** — 영수증 컨셉에서
  유일하게 살릴 가치가 있는 부분이고, 스팸으로 읽힌 건 색과 질감이지 표 구조가 아니었다

**토큰 구조**: 갈래마다 `--cN-bg / -ink / -soft / -key` 4개 한 벌 + `--on-key`(key를 배경으로
깔았을 때의 글자색). 컴포넌트는 `.c1/.c2/.c3`가 지역 변수 `--tone-*`로 받아쓰므로 **카드 규칙을
한 번만 쓴다**. CalcPage가 갈래 클래스를 씌우면 그 안의 Breakdown(칩·세그먼트·포커스링·공유
버튼)까지 자동으로 같은 색이 된다.

**설명 텍스트에 opacity를 쓰지 않는다.** 색이 배경과 블렌딩되면 대비를 계산할 수 없어서
접근성 회귀를 눈으로 못 잡는다. `--cN-soft`처럼 실제 색으로 못 박았다.

**docNo 폐기**: 계산기에 `No. 01` 같은 번호를 달고 있었는데 그 순서는 아무 의미가 없었다.
갈래 이름(급여·노동/부동산/금융)으로 바꿔 홈의 컬러 블록과 연결했다 — 구조적 장치는 내용에
대해 참인 것을 담아야 한다.

**검증**: 10페이지 × 라이트·다크 = 20회 axe 검사 0건. 이 과정에서 잡은 것:
`문장 속 링크는 색만으로 구분하면 안 된다`(WCAG 1.4.1) — 갈래 링크가 주변 회색 텍스트와
색 대비 1.0~1.4:1이라 **밑줄 상시 표시**로 해결.

## 2026-07-31 — 폰트: Pretendard Variable + JetBrains Mono

그동안 웹폰트 없이 시스템 스택(윈도우에서는 맑은 고딕)이었다. 후보 4조합을 실제로 붙여
비교(`?f=a~d`)한 뒤 **A. Pretendard + JetBrains Mono**로 확정.

- 본문/제목: **Pretendard Variable** — 한국어 서비스에서 사실상 표준이고, 가변 폰트라
  weight 45~920을 파일 하나로 커버한다
- 숫자: **JetBrains Mono** — 0에 슬래시가 있어 6/8과 헷갈리지 않는다. 계산기라 자릿수 정렬이
  생명이므로 금액은 예외 없이 등폭 + `tabular-nums`

**Pretendard는 npm 패키지로 import하면 빌드가 죽는다.** `pretendard/dist/.../
*-dynamic-subset.css`는 한글 유니코드 범위별 @font-face가 92개(가변)~828개(정적)라
webpack의 CSS 파서가 `RangeError: Maximum call stack size exceeded`로 터진다.
**dev는 통과하고 `next build`에서만 실패**해서 늦게 발견됐다.
→ 가변 폰트 CSS + woff2를 `public/fonts/pretendard/`로 복사하고 `<link rel="stylesheet">`로
직접 건다. 번들러를 아예 거치지 않으므로 안전하고, dynamic subset이라 브라우저는 **실제로
쓰인 범위만** 내려받는다(계산기 페이지 실측 13개 파일 332KB).

## 2026-07-31 — 콘텐츠 전략: 페이지를 "쓰지" 않고 "생성한다"

계산기 8종을 다 만들고 나니 **성장 엔진이 없다**는 게 드러났다. 페이지 10개에서 멈추고,
`/changes`는 연도가 하나뿐이라 변화 기록이 아니라 현재 기준 나열이었다. 콘텐츠를 어떻게 채울지
정리하면서 내린 결론:

**LLM으로 블로그 글을 양산하지 않는다.** 이 사이트의 제1원칙이 "계산이 틀리면 끝이다"인데,
근거 없는 해설 글은 그 신뢰를 깎는다. 모든 콘텐츠는 `rates.json` + 계산 함수에서 **파생**되게
유지한다. 그래야 제도가 바뀔 때 전 페이지가 한 번에 갱신되고, 그게 남들과 다른 유일한 지점이다.

### 1) 과거 연도 데이터 (2024·2025)

코드 수정 0, 데이터만 추가했는데 효과가 가장 컸다. `/changes`가 진짜 diff가 됐고, 계산기의
연도 선택이 의미를 갖게 됐다. 검증 경위는 [[rates-log]].

**`/changes`는 변경 내역을 손으로 적지 않는다.** `lib/diff.ts`가 연도 간 값을 비교해 자동 생성한다
— 손으로 적으면 데이터와 설명이 반드시 어긋나기 때문. "동결"도 정보라서 안 바뀐 항목도 한 줄로
남긴다.

### 2) 프로그래매틱 페이지 `/salary/[man]` (81개)

- 고정 가정(부양가족 1인, 자녀 0, 비과세=식대 한도)을 화면에 **그대로 표시**한다.

- 앞뒤 연봉·주요 연봉 내부 링크로 크롤링 경로를 만든다
- `dynamicParams = false` — 범위 밖(`/salary/1234`)은 얇은 페이지 대신 확실한 404

**조합을 폭발시키지 않는다.** 연봉×부양가족×비과세로 늘리면 수만 페이지가 되고 그건 스팸이다.

## 2026-07-31 — "다른 류의 계산기" 판단 기준과 4종 추가

운영자가 수학·환율 같은 다른 갈래를 물었다. 넣을지 말지를 감으로 정하지 않으려고 기준을 세웠다.

### 필터: 두 가지를 통과해야 넣는다
1. **네이버가 직접 답을 주지 않는가?**
2. **근거로 보여줄 제도가 있는가?**

**떨어뜨린 것** — BMI, 단위변환(평↔㎡), 순수 수학, 날짜/D-day, 만 나이, 시장 환율.
네이버·구글이 검색 결과 최상단에서 직접 답을 줘서 클릭이 오지 않고, "근거"라고 보여줄 게 없다.
세금 계산기를 포털이 안 하는 건 책임 리스크 때문이고 **그게 우리 자리다.**

### 추가한 것

**1. 역산 — 실수령액 → 연봉** (`/calc/reverse-salary` + `/net-salary/[man]` 56페이지)
"월 300 받으려면 연봉 얼마"는 검색 수요가 있는데 계산기가 거의 없다.
소득세가 누진세라 닫힌 역함수가 없어서 **이분 탐색**으로 뒤집었다. 실수령액이 연봉에 대해
단조증가라 안전하다. 연봉은 만원 단위로 **올림** — 협상 단위가 그렇고, 목표에 모자라지 않는 쪽.
정방향과 같은 함수를 쓰므로 **왕복 테스트**로 두 경로가 어긋나지 않게 못 박았다.

**2. 4대보험 사업주 부담** (`/calc/employer-cost`)
지금까지 전부 근로자 대상이었다. 이건 **사업자라는 새 사용자층**을 연다.
- 국민연금·건강보험·장기요양은 노사 절반씩이라 요율이 같다
- 고용보험은 실업급여분만 절반씩, 고용안정·직업능력개발분(0.25~0.85%)은 사업주 전액
- 산재보험은 업종별 고시라 **입력받는다**
"회사가 쓰는 돈 vs 직원이 받는 돈"을 한 화면에 나란히 놓는 게 이 계산기의 핵심.

**3. 정규직 vs 프리랜서 3.3%** (`/calc/employment-compare`)
비교 계산기는 남들이 잘 안 한다. 계산 함수를 이미 둘 다 갖고 있어서 붙이기만 하면 됐다.
**숫자만 보면 틀린 결론이 나오는 대표적인 경우**라, "숫자에 안 나오는 것"(4대보험 절반 부담·
퇴직금·연차·실업급여)을 두 번째 표로 반드시 같이 보여준다.

**4. 환전** (`/calc/exchange`)
실시간 환율은 만들지 않았다. 대신 **한국수출입은행 고시환율**(영업일 11시 전후 1회)을 쓴다.
- 공식 고시라 이 사이트 원칙과 맞고, 하루 1회라 ISR(`revalidate: 3600`)로 충분하다
- 우리가 답하는 질문은 "달러 환율 얼마"가 아니라 **"1,000달러 환전하면 실제로 얼마 드나"** —
  매매기준율 + 스프레드 + 우대율. 이건 포털이 안 준다
- **스프레드는 은행이 정하는 값이라 공식 고시가 아니다 → 추정하지 않고 입력받는다**
- 환율을 못 가져오면 **지난 값을 슬쩍 보여주지 않는다.** 언제 값인지 모르는 환율은 틀린 환율이라,
  왜 없는지 설명하는 빈 상태를 보여준다

⚠️ **`KOREAEXIM_API_KEY` 환경변수가 필요하다.** 발급은 수출입은행에서 본인인증 후.
키가 없으면 지금처럼 빈 상태가 나온다(빌드는 정상).

손해다. 허브는 위에 얹기만 했다. 허브 자체도 "○○ 계산기 모음" 검색어를 받는 페이지가 된다.

`/tax` 같은 최상위 경로 대신 **`/c/tax`**로 한 이유: 이미 `/salary`, `/car-tax`, `/property-tax`,
`/net-salary` 같은 최상위 라우트가 많아서 이름 충돌 위험이 크다. prefix 하나로 그 위험을 없앴다.

### 홈 — 목록이 아니라 답

맨 위에 **자주 찾는 답 7개**를 실제 숫자로 박았다. "연봉 3,000만원이면 실수령 얼마?" → "월 2,265,670원".
계산기 목록만 늘어놓으면 사용자는 한 번 더 눌러야 답을 보고, 검색엔진은 이 페이지가 무엇에
답하는지 알 수 없다.

**답은 전부 빌드 시각에 계산 함수로 구한다**(`lib/quickAnswers.ts`). 손으로 적으면 요율이 바뀔 때
조용히 거짓말이 된다 — `/changes`를 손으로 안 적는 것과 같은 이유.

카테고리별로는 **대표 계산기 3개 + "N개 더" 카드**만 보여준다. "N개 더" 카드는 계산기가 아니라
안내라서 점선 테두리로 눌러 구분했다.

### 계산·단위 카테고리 신설 — 입장 수정

앞서 "수학 계산기는 사이트 논지를 흐린다"고 반대했는데, **카테고리로 격리하면 그 문제가
사라진다.** 그 부분은 판단이 틀렸다. 다만 나머지 이유(포털이 직접 답을 줘서 클릭이 안 온다)는
그대로라, **본체 계산기로 이어지는 것만** 넣었다.

| 계산기 | 이어지는 곳 | 근거 |
|---|---|---|
| 평 ↔ ㎡ | 취득세 (85㎡가 농특세 경계) | 1평 = 400/121㎡ |
| 부가가치세 | 사업주·중개수수료 | 부가가치세법 제30조 |
| 퍼센트 | 연봉 인상률 | — |
| 예·적금 이자 | 이자소득세 15.4% | 소득세법 제129조 |

**안 넣은 것**: 공학용 계산기, 삼각함수, 진법변환 — 포털이 답을 주고 우리 쪽으로 이어지는 길도 없다.

### 카탈로그 단일화 — `lib/catalog.ts`
홈·카테고리 허브·사이트맵이 전부 이 배열 하나만 본다. 계산기 목록을 손으로 관리하는 배열이
두 벌이면 **반드시 어긋난다**(사이트맵에 `CALCS` 문자열 배열이 따로 있었고, 이미 새 계산기가
빠져 있었다). 테스트로 경로 중복·slug 중복·tone 중복·featured 누락을 검사한다.

### 방어한 것
- **`pct()`류 0 나누기** — 증감률에서 기준값이 0이면 Infinity가 나온다. "계산 불가"로 표시.
- **부가세 되짚기** — 합계에서 10%를 빼면 틀린다(1.1로 나눠야 함). 흔한 실수라 회귀 테스트로 못 박았다.

## 2026-07-31 — 상단 내비게이션: 카테고리 탭 + hover 드롭다운 (JS 없음)

시안 4종(헤더 탭 / 메가 드롭다운 / 컬러 칩 바 / 탭+서브바)을 만들어 비교했고,
운영자가 **2번의 드롭다운 + 4번의 헤더 모양**을 합치기로 했다.
결과: 카테고리 탭에 마우스를 올리면 그 카테고리의 계산기가 **전부** 펼쳐진다.

### JS를 쓰지 않았다

```css
.item:hover .panel,
.item:focus-within .panel { visibility: visible; opacity: 1; }
```

`:hover`로 열고 **`:focus-within`으로도** 연다. 이게 핵심이다 —
hover만 쓰면 키보드 사용자는 메뉴에 접근할 방법이 아예 없다.
`:focus-within` 하나로 Tab 키만으로 같은 메뉴가 열리고, 그대로 Tab을 눌러 안쪽 링크로 들어간다.
(검증: Playwright로 Tab 두 번 → 패널 `visibility: visible` 확인)

**터치 기기**는 hover가 없으므로 `@media (hover: none)`에서 드롭다운을 아예 끈다.
탭을 누르면 카테고리 허브(`/c/[slug]`)로 이동하므로 길이 막히지 않는다.
드롭다운을 억지로 탭-토글로 만들면 "첫 탭은 메뉴 열기, 두 번째 탭은 이동" 같은 헷갈리는
동작이 생긴다 — 그것보다 허브로 바로 보내는 게 낫다.

### 빠뜨리기 쉬운 것 두 가지

1. **탭과 패널 사이의 틈** — `top: calc(100% + 0.6rem)`처럼 띄우면 마우스가 그 틈을 지나는 순간
   hover가 풀려 메뉴가 닫힌다. 패널을 `top: 100%`에 붙이고 **패널 자체의 `padding-top`**으로
   시각적 간격을 만들어 마우스 경로가 끊기지 않게 했다.
2. **마지막 카테고리의 오른쪽 넘침** — `.item:last-child .panel { left: auto; right: 0; }`으로
   왼쪽으로 펼치게 했다. 안 그러면 뷰포트 밖으로 나간다.

계산기가 12개인 급여·세금은 패널을 2열로 나눈다(`.panelWide`) — 1열이면 세로로 너무 길어진다.

### 정리한 것
- `globals.css`의 `.site-header`/`.site-nav`/`.wordmark` 규칙(879자)을 지웠다.
  헤더가 `components/SiteNav`로 옮겨가면서 죽은 CSS가 됐다.
- 헤더의 "연봉" 링크를 뺐다 — 카테고리 탭이 생겨서 중복이다.
- 시안 라우트(`app/preview/`)는 역할이 끝나 삭제했다.
